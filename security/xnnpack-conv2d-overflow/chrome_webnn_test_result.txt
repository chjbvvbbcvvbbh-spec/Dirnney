RESULT: GUARDED — Chrome validates tensor size before XNNPACK
═══════════════════════════════════════════════════════════════

Chrome 150's WebNN implementation rejects the malicious dimensions at the
MLGraphBuilder.input() call in the Blink JavaScript layer.  The TypeError is
thrown before any XNNPACK reshape_igemm / indirection buffer code is reached.

Guard location (inferred from error message):
  Blink: modules/ml/webnn/ml_graph_builder.cc
  Check: totalByteLength > numeric_limits<size_t>::max() or similar

  Product rejected:
    1 × 506,164,742 × 506,168,762 × 1 × sizeof(float)
    = ~1,024 exabytes  →  "The number of elements is too large."

═══════════════════════════════════════════════════════════════
IMPLICATION
═══════════════════════════════════════════════════════════════

Chrome is NOT directly exploitable via navigator.ml in version 150 because
Blink performs an element-count overflow check before the descriptor is passed
to the XNNPACK backend.

However, the underlying XNNPACK library vulnerability (convolution-nhwc.c:2624)
remains unpatched and is reachable via:

  1. TFLite (tflite-runtime 2.14.0) — confirmed MemoryError / bad_alloc
  2. Direct XNNPACK API — confirmed SIGSEGV (release) and heap-buffer-overflow (ASAN)
  3. Any embedding without a Blink-equivalent dimension guard
  4. Older Chrome/WebNN versions that may lack the guard
  5. Android TFLite / ML Kit apps using XNNPACK CPU backend
