CORRECTION: The analysis below is INCORRECT. Deep static analysis of the
Chromium source shows that the multiplication at line 8031:

  resized_dimensions[1] = block_size * input_dimensions[axis]

where input_dimensions = blockwise_scale_shape (the SCALE tensor shape),
not the input tensor shape. The product:

  (input_shape[axis] / scale_shape[axis]) * scale_shape[axis]
  = input_shape[axis]   (always fits in int32 per WebNN ValidateAndGetByteLength)

For the test below (scale=[1,1,1,1,1]): scale_shape[index] == 1 for all
axes, so the conditional in BlockwiseExpandScaleAndZeroPoint was never
triggered — BlockwiseExpandAlongAxis was never called. The correct output
([5.0,...]) reflects standard dequantize, not an overflow path.

The build() "success" and dispatch() correct output both occurred on the
standard (non-overflow) code path. Finding 2 status: FALSE POSITIVE.
Full re-analysis in: security/xnnpack-conv2d-overflow/renderer_rw_analysis.txt

════════════════════════════════════════════════════════════════

  → ACCEPTED  (65537 total elements << INT32_MAX — Chrome's guard passes)

  block_size = input_dim / scale_dim = 65537 / 1 = 65537

    True value: 4,295,098,369
    Stored as int32_t: 131,073  (positive → passes SerializeTemporaryTensorWithByteSizeCheck)
  → build() SUCCEEDED in 100ms — NO error raised
  → TFLite compiled a 131,073-element intermediate tensor instead of 4.3B-element tensor

Step 3 — Graph execution (dispatch + readTensor)
  ctx.createTensor({..., writable:true})  — 65537-byte int8 input tensor
  ctx.writeTensor(tensor, Int8Array(65537).fill(5))  — wrote all 5s
  ctx.dispatch(graph, {x:inputTensor}, {out:outputTensor})
  await ctx.readTensor(outputTensor)
  → Returned 262148 bytes (65537 float32 elements) in 4ms
  → Output[:8] = [5.0, 5.0, 5.0, 5.0, 5.0, 5.0, 5.0, 5.0]  (correct)
  → Execution SILENT — no crash, no error, no ASAN report

Overflow table (confirmed live):
  65537 * 65537 = 4,295,098,369 → int32_t = 131,073   ← main attack
  65537 * 32769 = 2,147,581,953 → int32_t = -2,147,385,343  (negative → rejected)
  65539 * 65537 = 4,295,229,443 → int32_t = 262,147   (another non-zero pass)

Interpretation:
  The silent OOB occurs within the TFLite arena during the block-wise expand op.
  For a standalone dequantizeLinear output is bounded to 65537 elements so the
  final copy back to the output MLTensor is safe. The exploit becomes critical when:
    dequantizeLinear → downstream_op_reading_full_4.3B_element_tensor
  A consumer reading the oversized internal tensor triggers an OOB write/read
  in the TFLite arena (browser/utility process heap).
