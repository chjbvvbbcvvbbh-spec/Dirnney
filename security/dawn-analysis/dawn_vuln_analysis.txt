FINDING A — CONFIRMED BUG (LOW-MEDIUM SEVERITY)
ComputePassEncoder.cpp:331 — uint32_t overflow in indirect dispatch validation
════════════════════════════════════════════════════════════════════════════

File:    src/dawn/native/ComputePassEncoder.cpp:331
Type:    uint32_t integer overflow → incorrect dispatch validation
Trigger: Compute pipeline with workgroup_size(X, Y, Z) where X*Y*Z > UINT32_MAX

Vulnerable code:
  const uint32_t wgInvocations =
      wgSize.width * wgSize.height * wgSize.depthOrArrayLayers;  // line 331
  uint32_t overflowValue = std::numeric_limits<uint32_t>::max();
  if (usesGlobalIndex) {
      overflowValue /= wgInvocations;  // line 334 — division by zero if overflow→0
  }

Issue:
  `wgSize.{width,height,depthOrArrayLayers}` are uint32_t values derived from the
  WGSL shader's @workgroup_size attribute. Their product is computed in uint32_t
  without overflow protection. If X*Y*Z overflows to 0:
    → Division by zero at line 334 → SIGFPE / DAWN_UNREACHABLE crash

  If X*Y*Z overflows to a non-zero value N < true product:
    → overflowValue = UINT32_MAX / N (larger than correct)
    → The indirect dispatch validation shader uses overflowValue to check if
      dispatchX * wgInvocations overflows — but with wrong wgInvocations,
      the check is too permissive, allowing more workgroups than GPU hardware
      can safely handle

Exploitability:
  The product X*Y*Z is also constrained by maxComputeInvocationsPerWorkgroup
  (max 256 default, 1024 spec max). At 1024 invocations, no uint32 overflow
  is possible (1024 << 2^32).

  For overflow: requires X*Y*Z > 4,294,967,296 with each dimension validated
  against maxComputeWorkgroupSizeX/Y/Z. WebGPU spec allows per-dimension limits
  up to 65535 (implementation-defined). If hardware reports:
    maxComputeWorkgroupSizeX = 65536 AND maxComputeInvocationsPerWorkgroup = 65536^2
  then X=65536, Y=65536, Z=1 → X*Y = 4,294,967,296 → uint32 = 0 → crash.

  In practice: no known GPU reports maxComputeInvocationsPerWorkgroup > 2048.
  The bug exists but requires hardware limits not present on shipping devices.

Severity: LOW-MEDIUM (GPU process crash, not code execution)
Chrome VRP: ~$500–$5,000 (DoS via crash in GPU process, requires unlikely limits)

Remediation:
  Replace line 331 with overflow-safe computation:
    uint64_t wgInvocations64 = uint64_t(wgSize.width) * wgSize.height
                                * wgSize.depthOrArrayLayers;
    if (wgInvocations64 > std::numeric_limits<uint32_t>::max()) {
        // wgInvocations is already validated > maxComputeInvocationsPerWorkgroup
        // so this should be unreachable; treat as validation error.
        return DAWN_VALIDATION_ERROR("workgroup_size product exceeds uint32");
    }
    const uint32_t wgInvocations = static_cast<uint32_t>(wgInvocations64);

FINDING B — BEHAVIOR BUG (LOW SEVERITY)
TextureD3D11.cpp:758,770 — uint32_t overflow in depthPitch calculation
════════════════════════════════════════════════════════════════════════════

File:    src/dawn/native/d3d11/TextureD3D11.cpp:758,770
Type:    uint32_t overflow → incorrect D3D11 depthPitch argument
Platform: Windows D3D11 backend only

Vulnerable code (WriteInternal):
  // Line 758 — 3D texture path:
  commandContext->UpdateSubresource1(GetD3D11Resource(), subresource, &dstBox, data,
                                     bytesPerRow, bytesPerRow * rowsPerImage, copyFlag);
                                     //             ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                                     //             uint32_t * uint32_t — can overflow

  // Line 770 — 2D array texture path:
  data += rowsPerImage * bytesPerRow;  // uint32_t arithmetic, pointer advance wrong

Issue:
  `bytesPerRow` and `rowsPerImage` are uint32_t. For large textures:
    bytesPerRow = blockInfo.byteSize * writeSize.width  (line 561)
    rowsPerImage = writeSize.height                      (line 563)

  Example with RGBA32Float (16 bytes/texel), 32768×32768:
    bytesPerRow  = 16 * 32768 = 524,288
    rowsPerImage = 32768
    uint64 product = 17,179,869,184 → uint32 = 0  (depthPitch=0 to D3D11)
    D3D11 behavior with depthPitch=0 for 3D texture: UNDEFINED/DRIVER-SPECIFIC

  The upstream validation uses Safe32x32(bytesPerRow, rowsPerImage) which
  correctly computes the 64-bit required bytes. But the D3D11 backend
  recalculates in uint32_t, producing a wrong value.

Impact:
  - D3D11 driver may reject call silently or misread source data
  - `data += 0` at line 770 causes all array layers to read from offset 0
    (same data repeated) — incorrect but data stays within allocated buffer
  - NOT exploitable for OOB memory access (reads stay within user's data)
  - May cause GPU-side incorrect texture data (rendering bug, not security)

Severity: LOW (behavior bug, no memory safety impact)
Chrome VRP: Unlikely to qualify (no memory safety violation)

Remediation:
  Upgrade depthPitch computation to uint64_t:
    uint64_t depthPitch = uint64_t(bytesPerRow) * uint64_t(rowsPerImage);
    DAWN_ASSERT(depthPitch <= std::numeric_limits<UINT>::max());
  Or limit accepted bytesPerRow × rowsPerImage before calling WriteInternal.

WELL-HARDENED AREAS (NO EXPLOITABLE BUGS FOUND)
════════════════════════════════════════════════════════════════════════════

Wire Protocol (renderer → GPU process IPC):
  - WireAlignSizeofN<T>(count): returns std::optional<size_t>;
    null (overflow) causes WireResult::FatalError before any allocation
  - ChunkedCommandHandler: maintains invariant putOffset + remainingSize == allocated_size;
    check `chunkSize > remainingSize` before memcpy prevents OOB write
  - Handle table (ObjectStorage.h): bounds check (id >= mKnown.size()),
    state check (AllocationState::Allocated), generation check prevent
    UAF and type confusion
  - ServerBuffer.cpp: explicit `> std::numeric_limits<size_t>::max()` guards
    on all uint64 → size_t conversions (offsets, sizes, handle info lengths)
  - InlineMemoryTransferService::WriteHandleImpl::DeserializeDataUpdate:
    strict `deserializeData.size() != target.size()` check prevents OOB

Native Backend Validation:
  - ComputeRequiredBytesInCopy: uses Safe32x32() for bytesPerRow*rowsPerImage,
    DAWN_INVALID_IF for depth overflow; correctly guards before allocations
  - BlockCount type alias is uint64_t (NOT uint32_t) — agent's Vulkan
    CommandBufferVk.cpp finding is a false positive
  - QueueBase::WriteTextureImpl: uses TypedTexelBlockInfo::ToBytes() which
    operates in uint64_t, then validates total bytes before upload

Tint WGSL Compiler:
  - kMaxParseDepth = 128 checked at two recursion entry points (lines 2662, 3449)
    prevents stack overflow from deeply nested WGSL
  - UNSAFE_TODO in binary_writer.cc (memcpy into pre-resized vector): safe
    because vector resized to OperandLength(op) words before memcpy of string
  - UNSAFE_TODO in symbol_table.cc: allocates name.length()+1 bytes before
    memcpy of name.length()+1 bytes — correct
  - No unguarded attacker-controlled malloc/realloc sizes found


════════════════════════════════════════════════════════════════════════════
COMPARISON: DAWN vs. GLES2 CMD DECODER (FINDING 1)
════════════════════════════════════════════════════════════════════════════

Dawn (WebGPU, this analysis):
  - Modern codebase with TypedInteger wrappers, std::optional for overflows,
    Safe32x32(), BlockCount=uint64_t
  - Wire protocol uses WireAlignSizeofN overflow protection throughout
  - Tint compiler has recursion depth guards
  - No confirmed exploitable memory safety bug found via static analysis

GLES2 cmd decoder (Finding 1, previous research):
  - gles2_cmd_decoder.cc:12629 — raw uint32_t arithmetic without overflow check:
    output_pixel_size * width * height * depth → UINT32 OVERFLOW
  - Legacy codebase without systematic overflow protection
  - CONFIRMED exploitable (GPU process heap overflow)

Conclusion: Dawn's security posture is significantly stronger than the GLES2
command buffer decoder. The architecture (TypedInteger, WireAlignSizeofN,
Safe32x32) prevents the class of overflow bugs that makes the GLES2 decoder
exploitable. Renderer→GPU escalation via Dawn wire is NOT immediately feasible.
