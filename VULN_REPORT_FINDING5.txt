================================================================================
VULNERABILITY REPORT
V8 JavaScript Engine — Homomorphic IC Double-Field Type Confusion
================================================================================

Title        : Turbofan CheckHeapObject Removed for OtherInternal-Typed Double
               Field Load in ReduceHomomorphicAccess — Controlled SIGSEGV /
               Cage-Relative Arbitrary Read Primitive
Severity     : P2 (pre-shipping; becomes P1/P0 if --homomorphic-ic ships by default)
Component    : V8 JavaScript Engine — Turbofan JIT Compiler
Affected ver : V8 15.0.39 (confirmed); likely all versions with homomorphic IC code
Platform     : x86_64 Linux (pointer-compression build)
Tested binary: ~/.jsvu/engines/v8/v8  (V8 15.0.39, release build, not stripped)
OS           : Linux 6.18.5 x86_64
Reporter     : Security audit of V8 source — js-native-context-specialization.cc
Status       : Unpatched (flag-gated, non-default)
Flag required: --homomorphic-ic  (default: false; enabled by --future)

================================================================================
1. EXECUTIVE SUMMARY
================================================================================

A type confusion vulnerability exists in V8's Turbofan JIT compiler within the
ReduceHomomorphicAccess function (js-native-context-specialization.cc:1884).

When a property field is Double-represented and the IC is in HOMOMORPHIC state,
ReduceHomomorphicAccess assigns Type::OtherInternal() to the field access node's
type annotation. A CheckHeapObject guard is added immediately after to protect
against a race: V8 can generalize a field from Double to Tagged representation
IN-PLACE (without a map transition), which would place a raw Smi in the field
slot where a HeapNumber pointer is expected.

The guard is then silently REMOVED by TypedOptimization::ReduceCheckHeapObject
(typed-optimization.cc:166) because Type::OtherInternal() (bitset bit 23) is
disjoint from Type::SignedSmall() (bitset bits 6 and 10), triggering the
elimination condition.

With the guard absent, and no kFieldRepresentationGroup dependency to deoptimize
the compiled code on field generalization, the following sequence achieves a
controlled read at an arbitrary offset within V8's pointer-compression cage:

  1. Force IC into HOMOMORPHIC state with 5 distinct maps (Double x field).
  2. Compile the accessor function to Turbofan (guard removed).
  3. Trigger in-place Double->Tagged field generalization via non-numeric store.
  4. Write a controlled Smi value into the now-Tagged field slot.
  5. Call the stale JIT code: LoadField(Map, Smi) dereferences Smi bits as pointer.

CONFIRMED: Reproduces as SIGSEGV (signal 11, SEGV_ACCERR) with a crash address
of exactly:

    crash_addr = cage_base + (controlled_smi * 2) - 1

for any attacker-controlled integer in Smi range (~30 bits on 64-bit V8).

================================================================================

Primary bug site:
----------------
  File   : src/compiler/js-native-context-specialization.cc
  Lines  : 1881–1907
  Func   : JSNativeContextSpecialization::ReduceHomomorphicAccess

  1881:  FieldAccess field_access =
  1882:      AccessBuilder::ForJSObjectOffset(kTaggedSize * offset_in_words);
  1883:  if (is_double) {
  1884:    field_access.type = Type::OtherInternal();   // <-- ROOT CAUSE
  1885:  }
  1886:  Node* result = effect = graph()->NewNode(
  1887:      simplified()->LoadField(field_access), holder, effect, control);
  1888:
  1889:  if (is_double) {
  1890:    // With in-place field representation changes it is possible that this
  1891:    // is no longer a heap number without map transitions (generalized from
  1892:    // Double to Tagged in-place). So we need to verify the loaded value
  1893:    // is a heap number.
  1894:    result = effect = graph()->NewNode(simplified()->CheckHeapObject(),
  1895:                                       result, effect, control);  // <-- GUARD
  1896:    Node* map = effect =
  1897:        graph()->NewNode(simplified()->LoadField(AccessBuilder::ForMap()),
  1898:                         result, effect, control);                // <-- USES result
  1899:    ...
  1907:  }

  The developer comment at line 1890 EXPLICITLY acknowledges the in-place
  generalization risk and adds CheckHeapObject to handle it. However, the
  type annotation OtherInternal at line 1884 causes the guard to be
  unconditionally eliminated one pipeline phase later.

Guard elimination site:
-----------------------
  File   : src/compiler/typed-optimization.cc
  Lines  : 166–174
  Func   : TypedOptimization::ReduceCheckHeapObject

  166:  Reduction TypedOptimization::ReduceCheckHeapObject(Node* node) {
  167:    Node* const input = NodeProperties::GetValueInput(node, 0);
  168:    Type const input_type = NodeProperties::GetType(input);
  169:    if (!input_type.Maybe(Type::SignedSmall())) {
  170:      ReplaceWithValue(node, input);   // <-- ELIMINATES THE GUARD
  171:      return Replace(input);
  172:    }
  173:    return NoChange();
  174:  }

  Condition at line 169:
    input_type = Type::OtherInternal()  (bitset: bit 23 = 0x00800000)
    Type::SignedSmall()                 (bitset: bits 6,10 = 0x00000440)
    OtherInternal & SignedSmall = 0     --> !Maybe(SignedSmall) == true
    --> CheckHeapObject unconditionally removed.

Type bitset definitions:
------------------------
  File   : src/compiler/turbofan-types.h
  Lines  : 95–131

    kOtherInternal = 1 << 23   // bit 23
    kUnsigned30    = 1 << 10   // bit 10  \
    kNegative31    = 1 <<  6   // bit  6  / SignedSmall = kUnsigned30 | kNegative31

  These sets are DISJOINT. The guard elimination logic was designed to be safe
  because Smis have SignedSmall type; OtherInternal should not include Smis.
  The bug is that the JIT annotates a field slot that CAN contain Smis (after
  generalization) with OtherInternal, which the type system treats as Smi-free.

In-place generalization path:
-----------------------------
  File   : src/objects/property-details.h
  Lines  : 157–169
  Func   : Representation::CanBeInPlaceChangedTo

  157:  bool CanBeInPlaceChangedTo(const Representation& other) const {
  158:    if (Equals(other)) return true;
  159:    if (IsWasmValue() || other.IsWasmValue()) return false;
  160:    if (IsNone()) return !other.IsDouble();
  161:    if (!other.IsTagged()) return false;
  162:    DCHECK(IsSmi() || IsDouble() || IsHeapObject());
  163:    return true;          // <-- Double -> Tagged: true
  164:  }

  Double.CanBeInPlaceChangedTo(Tagged) returns TRUE.
  MapUpdater (map-updater.cc:740-754) takes the in-place update path,
  keeping the map at the same address. The map does NOT change, so
  CheckHomomorphic (which hashes map addresses) still passes.

Missing dependency registration:
---------------------------------
  File   : src/compiler/property-access-builder.cc
  Lines  : 287–348
  Func   : PropertyAccessBuilder::BuildLoadDataField

  The SAFE path (regular Turbofan property access) for Double fields calls:
    dependencies()->DependOnFieldRepresentation(...)
  This registers a kFieldRepresentationGroup dependency. When the field is
  later generalized, MapUpdater::GeneralizeField deoptimizes all code with
  this dependency.

  ReduceHomomorphicAccess NEVER calls DependOnFieldRepresentation.
  No dependency is registered. Generalization does NOT deoptimize the JIT code.

IC state machine:
-----------------
  File   : src/ic/ic.cc
  Lines  : 553–631
  Func   : IC::UpdateHomomorphicIC

  Transition POLYMORPHIC -> HOMOMORPHIC occurs when:
    - IC has 4+ distinct maps (poly limit exceeded)
    - All existing handlers == new handler (same field descriptor)
  This creates a WeakHomomorphicFixedArray (capacity = homomorphic_ic_count,
  default 8) storing the seen map pointers.

3. ROOT CAUSE CHAIN
================================================================================

Step 1  [Phase: InliningPhase / JSNativeContextSpecialization]
        ReduceHomomorphicAccess is called for a Double field.
        field_access.type is set to Type::OtherInternal() (line 1884).
        Node graph emitted:

          #25: LoadField[offset=12, type=OtherInternal]  <-- loads HeapNumber* or Smi
          #26: CheckHeapObject(#25)                       <-- guard (correct intent)
          #27: LoadField[Map, offset=0](#26)              <-- reads map FROM #26
          #28: HeapConstant[HeapNumberMap]
          #29: ReferenceEqual(#27, #28)
          #30: CheckIf[NotAHeapNumber](#29)
          #31: LoadField[HeapNumberValue, offset=4](#26)  <-- reads float value

Step 2  [Phase: TypedLoweringPhase / TypedOptimization]
        ReduceCheckHeapObject visits node #26.
        input_type = Type::OtherInternal() (from #25).
        !OtherInternal.Maybe(SignedSmall) == true.
        Node #26 REPLACED by node #25 (its input, the raw load).
        After replacement: #27, #31 now take #25 (raw load) as value input.

        Node graph after elimination:
          #25: LoadField[offset=12, type=OtherInternal]  <-- same
          (no CheckHeapObject)
          #27: LoadField[Map, offset=0](#25)             <-- NOW reads map from RAW load
          #30: CheckIf[NotAHeapNumber](...)
          #31: LoadField[HeapNumberValue, offset=4](#25)

Step 3  [Runtime: Field generalization]
        receivers[2].x = "string" is executed at runtime.
        MapUpdater::GeneralizeField: Double -> Tagged, in-place (same map address).
        No kFieldRepresentationGroup dependency exists on readX Turbofan code.
        readX is NOT deoptimized.

Step 4  [Runtime: Smi stored in Tagged field]
        receivers[2].x = 0x1eadbeef is executed.
        Field descriptor is now Tagged. StoreIC stores 0x1eadbeef as Smi directly
        (not as HeapNumber box). Field slot at offset 12 now contains:
            Smi(0x1eadbeef) = 0x3d5b7dde  (tagged: value << 1)

Step 5  [Runtime: Stale JIT code executes]
        readX(receivers[2]) called through Turbofan-compiled code.

        CheckHomomorphic: map of receivers[2] unchanged (in-place modification) ->
            map address still in WeakHomomorphicFixedArray -> PASS.

        #25 = LoadField[offset=12]: returns 0x3d5b7dde  (Smi, 32-bit compressed)

        #27 = LoadField[Map, offset=0](0x3d5b7dde):
            V8 computes effective address:
                cage_base + 0x3d5b7dde - kHeapObjectTag(1)
              = cage_base + 0x3d5b7ddd
            Reads 8 bytes from this address.

        This address is NOT mapped -> SIGSEGV (SEGV_ACCERR).

5. EXPLOITATION PRIMITIVE
================================================================================

The confirmed primitive is:

    read8(offset) where offset = controlled_smi * 2 - 1

within the V8 pointer-compression cage (4 GB window at cage_base).

  controlled_smi range : 1 to (2^30 - 1)  (V8 Smi range on 64-bit)
  readable range       : cage_base + 1 to cage_base + 2^31 - 3
  granularity          : any odd offset (even alignment via controlled_smi + 0.5 N/A)

In practice, with a Smi value of N, the read is at:
    cage_base + 2N - 1

All V8 heap objects (JSObjects, Maps, FixedArrays, etc.) live within the cage.
A controlled read over the cage can leak:
  - Pointer values (other heap object addresses)
  - Map addresses (enabling type confusion pivot)
  - Array buffer backing store pointers
  - JSFunction code pointers

Combining this with Finding 3 (Smi address-range guard silent failure) or a
second Smi-as-pointer confusion allows reads below cage_base as well.

6. TRIGGER REQUIREMENTS
================================================================================

1. --homomorphic-ic flag must be active.
   Default: false. Enabled by: --homomorphic-ic or --future.
   NOT enabled in Chrome, Node.js, or Deno with default settings.

2. Exactly 4 < N <= homomorphic_ic_count distinct object maps with same field.
   - N > 4: overflow V8 polymorphic IC limit -> POLY->HOMOMORPHIC transition.
   - N <= 8 (default homomorphic_ic_count): all maps fit in WeakHomomorphicFixedArray.
   - If N > 8: some maps missing from array -> CheckHomomorphic fails -> safe deopt.
   PoC uses N=5 (5 distinct maps, sufficient and minimal).

3. All N objects must have the target property (x) as a Double-represented field
   at the SAME in-object offset and with the SAME load handler Smi.

4. Turbofan must compile the accessor (not Maglev; ReduceHomomorphicAccess is
   Turbofan-only). Enforce with --no-maglev or enough iteration count.

5. Generalization trigger: assign a non-numeric value (string, object) to x on
   any object sharing the parent map. This forces in-place Double->Tagged
   generalization (CanBeInPlaceChangedTo returns true; map address unchanged).
   Do NOT use an integer assignment first: integers are boxed as HeapNumber,
   leaving the field as Double (no generalization).

6. After generalization: assign controlled integer to x.
   The field is now Tagged; the integer is stored as a raw Smi (not HeapNumber).

7. Call the Turbofan-compiled accessor. Crash occurs at:
   cage_base + (controlled_smi * 2) - 1.

================================================================================
7. WHY THE EXISTING GUARDS DO NOT CATCH IT
================================================================================

Guard 1: CheckHeapObject (intended guard)
  Status  : REMOVED by TypedOptimization (the bug).
  Reason  : input type = OtherInternal, disjoint from SignedSmall.
            ReduceCheckHeapObject condition fires; node replaced by raw input.

Guard 2: CheckIf[NotAHeapNumber]
  Status  : UNREACHABLE when field holds Smi.
  Reason  : CheckIf consumes the result of LoadField[Map](#25). If #25 is Smi,
            LoadField[Map, offset 0](Smi) crashes BEFORE CheckIf ever evaluates.
            CheckIf would only save execution if the pointer read succeeded and
            returned a non-HeapNumber map. With a Smi address this cannot happen.

Guard 3: CheckHomomorphic
  Status  : PASSES (this is the key insight).
  Reason  : In-place field generalization does not change the map address.
            The WeakHomomorphicFixedArray still contains the unchanged map pointer.
            Hash lookup succeeds; no deopt.

Guard 4: kFieldRepresentationGroup deoptimization dependency
  Status  : ABSENT in homomorphic IC path.
  Reason  : ReduceHomomorphicAccess never calls DependOnFieldRepresentation.
            MapUpdater::GeneralizeField fires kFieldRepresentationGroup deopt only
            on code that registered this dependency. readX has none -> survives.

Guard 5: Smi address-range guard (sandbox.cc:317)
  Status  : Potentially absent (see Finding 3).
  Reason  : If AllocateGuardRegion failed silently, low addresses are unguarded.
            Even with the guard active, cage_base + 2N - 1 for N in Smi range
            is far above the guard region (which covers [0, ~1 MB]).
            The crash at cage_base + ~1 GB is not in the guard region.

================================================================================
8. COMPARISON WITH THE SAFE PATH
================================================================================

The regular Turbofan property access path (property-access-builder.cc:287-348,
function BuildLoadDataField) handles the same scenario correctly via TWO
distinct safe strategies:

Strategy A: No dependency tracking (dependencies() == nullptr)
  field_access.type = Type::Any()
  Type::Any() includes SignedSmall.
  ReduceCheckHeapObject: Any.Maybe(SignedSmall) == true -> guard NOT removed.
  Outcome: CheckHeapObject survives; Smi in field triggers safe deopt.

Strategy B: With dependency tracking
  dependencies()->DependOnFieldRepresentation(...)
  Registers kFieldRepresentationGroup dependency.
  MapUpdater::GeneralizeField deoptimizes the JIT code before any Smi
  can be stored in the field slot.
  Outcome: Code deoptimized before reaching the vulnerable state.

ReduceHomomorphicAccess uses NEITHER strategy:
  - Uses Type::OtherInternal() instead of Type::Any() -> guard removed.
  - Does not call DependOnFieldRepresentation -> no deopt on generalization.

10. REMEDIATION
================================================================================

Option A (preferred — fix the type annotation):
  Change line 1884 from:
      field_access.type = Type::OtherInternal();
  to:
      field_access.type = Type::Any();
  This matches the safe strategy used by BuildLoadDataField when no dependency
  tracking is available. Type::Any includes SignedSmall, so ReduceCheckHeapObject
  will leave the guard intact.

Option B (defence-in-depth — add dependency):
  Before emitting the field load in ReduceHomomorphicAccess, call:
      if (dependencies()) dependencies()->DependOnFieldRepresentation(...);
  This ensures in-place generalization deoptimizes the compiled code.
  May be impractical because homomorphic IC operates over MANY maps.

Option C (belt-and-suspenders):
  Apply both A and B. Option A fixes the immediate guard removal. Option B
  adds the missing deoptimization dependency as a second line of defense.

Option D (quick workaround):
  In TypedOptimization::ReduceCheckHeapObject, also check for OtherInternal:
      if (!input_type.Maybe(Type::SignedSmall()) &&
          !input_type.Is(Type::OtherInternal())) {
        ReplaceWithValue(node, input);
        ...
      }
  This prevents elimination when the input type is OtherInternal.
  Not ideal since it treats the symptom rather than the root cause.

================================================================================
11. DISCLOSURE NOTES
================================================================================

- The vulnerable code is currently gated by --homomorphic-ic (default: false).
  It is NOT exploitable in shipping Chrome, Node.js, or Deno.

- If --homomorphic-ic is enabled by default (via --future graduating or explicit
  shipping), this becomes an immediately exploitable P1/P0 bug in V8.

- The developer comment at line 1890 shows awareness of the in-place
  generalization risk; the CheckHeapObject guard was added deliberately.
  The specific interaction with TypedOptimization that removes the guard
  appears to be an oversight.

- Report to the V8 security team at security@chromium.org before the
  --homomorphic-ic feature is enabled by default.
